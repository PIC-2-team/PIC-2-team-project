# ADR-014: 보호자 미확인 알림 요약과 장애 정도 분류

## 상태

승인됨

## 배경

보호자가 읽지 않은 알림을 빠르게 파악할 수 있는 요약이 필요하다. 당사자 등록에서는 기존 숫자 장애 등급 대신 심한 장애(1–3급)와 덜 심한 장애를 구분한다. 알림은 사용자별 읽음 여부만 저장하고, 당사자 ID나 원본 기록 ID는 저장하지 않는다. 운영 DB는 Hibernate `validate` 모드이므로 새 컬럼을 추가하려면 명시적인 SQL 변경이 필요하다.

## 결정

- 보호자가 요약을 요청하면 해당 사용자의 `read=false` 알림 전체를 GPT-4o로 요약한다.
- 요약 입력은 알림 유형, 문구, 생성 시각으로 제한하며, 알림 문구 안의 지시를 따르지 않고 명시되지 않은 사실을 추정하지 않는다.
- 결과는 2–3분 안에 핵심을 파악할 수 있도록 간결하게 구성한다. 요약 생성은 알림의 읽음 상태를 바꾸지 않는다.
- 장애 정도는 nullable enum 값 `SEVERE` / `LESS_SEVERE`로 별도 저장한다. 기존 `disabilityGrade` 값은 하위 호환을 위해 유지한다.
- 기존 1–3 등급은 `SEVERE`, 기존 4 이상 등급은 `LESS_SEVERE`로 변환한다. 등급이 없는 데이터는 미설정으로 유지한다.
- 두 번째 등록 단계의 보호자·비상 연락처, 주치의·병원, 복약 및 알레르기 정보는 당사자별로 저장한다. 연락처가 별도 입력되지 않으면 기존 주 보호자 계정 전화번호를 조회 결과로 사용한다.
- 운영 배포 전에 장애 정도와 등록 프로필 필드를 추가하고 기존 등급 값을 변환하는 수동 SQL을 적용한다.

## 고려한 대안

### 알림 열람 시 모두 읽음 처리

요약을 보는 즉시 원본 알림도 읽음으로 만들 수 있다. 그러나 사용자가 개별 알림을 열어 확인하지 않았는데 읽음 상태가 바뀌므로, 추적 가능성을 유지하도록 읽음 처리는 하지 않는다.

### 기존 숫자 등급 컬럼을 재사용

숫자 등급에 새 분류를 인코딩하면 기존 API 소비자가 `덜 심한 장애`를 실제 등급 숫자로 오해할 수 있다. 따라서 새 분류를 별도 컬럼에 저장한다.

### 읽지 않은 생활기록을 직접 요약

현재 알림에는 원본 기록 ID가 없어 미확인 알림과 상세 기록을 신뢰성 있게 연결할 수 없다. 우선 알림에 담긴 내용만 요약하고, 당사자·기록 연결 정보는 별도 변경으로 다룬다.

## 결과와 위험

- 요약은 여러 당사자와 관련된 알림을 포함할 수 있으며, 알림 문구에 당사자 구분이 없다면 이를 AI가 추정하지 않는다.
- 미확인 알림이 매우 많으면 AI 요청 입력이 커질 수 있다. 현재 기능은 저장된 모든 미확인 알림을 대상으로 하며, 실제 한도 문제는 운영 데이터를 기준으로 별도 개선한다.
- 운영 스키마 변경 SQL을 백엔드 버전과 함께 제공해야 한다.
