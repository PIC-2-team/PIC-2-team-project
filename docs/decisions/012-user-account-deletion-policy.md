# ADR-012: 회원 탈퇴 시 데이터 처리 정책

## 상태

승인됨

## 맥락

`DELETE /api/users/me` 구현을 위해 탈퇴 시 소유 데이터의 처리 방식을 결정해야 한다.

삶결 서비스의 핵심 데이터인 `CareRecipient`와 `DailyRecord`는 보호자 계정에 귀속되지만, 발달장애인 당사자의 돌봄 연속성을 위해 기관과 활동지원사가 지속적으로 필요로 한다. 단순 완전 삭제는 돌봄 연속성을 끊는 역설을 만든다.

### 검토한 대안

**대안 A — 완전 삭제 (Hard Delete)**
- 탈퇴 즉시 계정·당사자·기록 전체 삭제
- 장점: 구현 단순, PIPA 데이터 파기 의무 이행이 명확
- 단점: 현재 배정된 활동지원사와 기관의 당사자 정보가 즉시 사라짐. 진행 중인 돌봄 서비스가 중단됨

**대안 B — 완전 익명화 (Anonymization Only)**
- 계정 개인정보를 익명화하고 당사자·기록 데이터는 유지
- 장점: 돌봄 연속성 보장
- 단점: 당사자 데이터의 "소유권"이 불명확해짐. 보호자가 데이터 삭제를 원하는 경우 이행 불가

**대안 C — 이관 선택 + 역할별 처리 (채택)**
- 탈퇴 전 보호자가 당사자 데이터 처리 방식을 선택
- 장점: 돌봄 연속성과 데이터 주체 권리를 모두 보장
- 단점: 구현 복잡도 증가, 이관 대상 기관이 없는 경우 처리 필요

## 결정

**이관 선택 + 역할별 처리** 방식을 채택한다.

### 역할별 처리 규칙

| 시나리오 | 처리 |
|---|---|
| 탈퇴 보호자가 당사자의 유일한 보호자 | 탈퇴 전 "기관에 이관" 또는 "데이터 삭제" 선택 강제 |
| 이관 선택 | 당사자 데이터는 기관에 귀속, 보호자 개인정보(이름·이메일·연락처)만 익명화 |
| 삭제 선택 | `CareRecipient` + 연관 기록 소프트 딜리트 → N일 후 하드 딜리트 |
| 세컨드 보호자 탈퇴 | 본인 계정·제안 이력만 익명화, 당사자 데이터 영향 없음 |
| 활동지원사·기관 탈퇴 | 본인 계정 익명화, 작성한 기록은 익명 작성자로 유지 |

### 추가 처리 규칙

- 탈퇴 시 활성 `RefreshToken` 및 세션 즉시 만료
- 소프트 딜리트 유예 기간 N은 운영 정책으로 결정 (7~30일 권장)
- 이관 시 기관 담당자에게 알림 발송
- 연결된 기관이 없는 보호자가 이관 선택 시 "연결된 기관이 없습니다" 안내 후 삭제만 허용

### PIPA 준수

개인정보보호법상 익명화는 파기로 인정된다(개인정보보호위원회 해석). 이관 선택 시 보호자 개인정보 익명화로 PIPA 제21조 파기 의무를 이행한다.

## 영향

- **BE:** `UserService.deleteUser()`, `CareRecipientService` 이관 로직, 소프트 딜리트 스케줄러
- **FE:** `MorePage.tsx` 탈퇴 플로우 — 이관/삭제 선택 다이얼로그
- **API-Spec:** `DELETE /api/users/me` 동작 확정 (기존 "파기 정책 미정" 상태 해소)
- **DB:** 익명화 대상 컬럼 정의 필요 (`users.name`, `users.email`, `users.phone`)
