# ADR-015: SMS 전화번호 인증 도입

## 상태

제안 — 공급자의 공식 단가와 발신번호 등록 절차를 확인하고, 비용을 부담할 주체(결제 수단 등록자)를 정한 뒤 승인한다. 비용은 예산을 확정하지 않고 "종량제 + 발송 한도 + 재검토 기준"으로 다룬다.

## 맥락

11-01 TODO에 "전화번호 및 SMS 인증 회원가입"이 있다. 코드를 확인한 현재 상태는 다음과 같다.

- 이메일 가입(`POST /api/auth/register`)은 전화번호를 **필수로 받지만 인증하지 않는다.** 형식만 검사한다(`^01[016789]-?\d{3,4}-?\d{4}$`).
- Google 가입(`/api/auth/google/register`)은 전화번호를 받지 않는다. `users.phone`은 nullable이고 DB 유니크 제약이 없다. 가입 시 앱 코드의 `existsByPhone`으로만 중복을 막는다.
- **전화번호가 본인 확인 수단으로 쓰이는데 소유 확인이 없다.**
  - `POST /api/auth/find-email`: 이름 + 전화번호가 일치하면 마스킹된 이메일을 알려 준다.
  - `POST /api/auth/reset-password`: 이메일 + 이름 + 전화번호가 일치하면 인증 없이 새 비밀번호로 바꾼다. 세 값을 아는 사람이면 누구나 계정을 탈취할 수 있다.
- `find-email`과 `reset-password`는 `permitAll` 공개 경로라 로그인 없이 호출된다.
- 남의 번호를 먼저 가입에 써서 그 사람의 가입을 막을 수도 있다(중복 검사만 있고 소유 확인이 없다).

이 서비스는 발달장애인의 민감한 돌봄 정보를 다루므로(ADR-007), 계정 탈취는 가장 큰 위험이다. SMS 인증은 가입 편의가 아니라 **재설정 경로의 본인 확인**을 위해 필요하다.

## 결정

### 1. 적용 범위 — 가입과 본인 확인 두 곳 모두

| 용도 | 동작 |
|---|---|
| 이메일 가입 | 번호 소유를 확인한 뒤 가입한다 |
| 비밀번호 재설정 | 이메일·이름·번호 일치에 더해 SMS 인증을 통과해야 한다 |
| 이메일 찾기 | 이름·번호 일치에 더해 SMS 인증을 통과해야 한다 |

- Google 가입은 전화번호를 받지 않으므로 이번 범위에서 제외한다(번호는 계속 null).
- 기존 가입자의 번호는 인증된 적이 없지만, 재설정·찾기 때 번호로 SMS 인증을 통과하면 그대로 쓸 수 있다. 번호를 잘못 기재한 기존 가입자는 복구할 수 없으므로 운영자 문의 경로를 안내한다.

### 2. 인증 방식 — 서버 발급 6자리 코드 + 인증 티켓

- 서버가 6자리 숫자 코드를 만들어 문자로 보낸다. 사용자가 코드를 입력하면 서버가 검증하고 **전화번호 인증 티켓**(JWT, 10분 유효, 1회 사용)을 발급한다. 가입·재설정·찾기 요청은 이 티켓을 함께 보낸다. 동의 티켓(ADR-007)과 같은 방식이다.
- 코드는 `phone_verification` 테이블에 **해시로만** 저장한다(원문 저장 금지). 컬럼은 전화번호(정규화), 코드 해시, 용도(`REGISTER` | `RESET_PASSWORD` | `FIND_EMAIL`), 만료 시각, 시도 횟수, 인증 시각, 생성 시각이다. Redis는 쓰지 않는다(ADR-004와 같은 이유).
- 제한(제안값, 구현 시 조정):

| 항목 | 값 |
|---|---|
| 코드 유효 시간 | 5분 |
| 오입력 | 5회 초과 시 해당 코드 무효 |
| 재전송 간격 | 60초 |
| 동일 번호 발송 | 시간당 5회, 일 10회 |
| 동일 IP 발송 | 시간당 20회 |

### 3. 공급자 — 국내 문자 발송 서비스 + 교체 가능한 구조

- 문자 발송은 `SmsSender` 인터페이스 뒤에 숨기고, 공급자별 구현을 갈아 끼울 수 있게 한다(`OpenAiConfig`와 같은 선택적 빈 패턴). 공급자 확정이 늦어져도 나머지 구현은 진행할 수 있다.
- 국내 번호로 문자를 보내려면 **발신번호 사전등록**이 필요하다. 업체 안내 기준 근거는 전기통신사업법 제84조의2이며, 정확한 조문은 국가법령정보센터에서 확인해야 한다. 사업자 서류나 통신서비스 이용증명원이 필요할 수 있어, 확정 전에 팀이 서류를 준비할 수 있는지 먼저 확인한다.
- 설정되지 않았거나 장애일 때는 `SMS_UNAVAILABLE`(503)로 응답한다. AI 초안의 `AI_UNAVAILABLE`과 같은 패턴이다.
- 개발·테스트 프로필에는 실제 발송 없이 로그에 코드를 남기는(번호는 마스킹) 구현을 쓴다. 운영 프로필에서만 실제 공급자를 호출한다. E2E 테스트는 고정 코드를 사용한다.

**공급자 비교** (아래 단가는 모두 확인된 출처를 적었고, 공식 확인이 안 된 값은 표시했다)

| 후보 | 단가 | 비고 |
|---|---|---|
| NHN Cloud Notification (SMS) | 건당 약 9.9원, 종량제, 최소 약정 없음 — **공식 요금표 미확인**, 블로그·비교 글 기준 | 국내 번호 발송에 맞음. 발신번호 등록 필요. 공식 확인 필요 |
| 알리고 등 국내 문자 대행 | **조사하지 못함** (공식 요금표 미확인) | 확인 필요 |
| Twilio Verify | 성공한 인증당 $0.05 + SMS 채널 요금([Verify 요금](https://www.twilio.com/en-us/verify/pricing)). 한국 SMS는 국제 번호 발신 기준 건당 $0.0524([한국 SMS 요금](https://www.twilio.com/en-us/sms/pricing/kr)) → 인증 1건에 약 $0.10 이상 | 인증 로직까지 맡아 주지만 NHN(비공식 값 기준)보다 단가가 크게 높다. 카드 결제가 필요하다 |

**제안**: NHN Cloud Notification을 우선 후보로 하되, 공식 단가·발신번호 등록 절차를 확인한 뒤 승인한다. 확인 결과 부적합하면 `SmsSender` 구현만 다른 공급자로 바꾼다.

### 4. 비용과 남용 방지 — 예산을 확정하지 않는 방식

- 종량제로 시작하고 최소 충전·월 기본료가 있는 요금제는 피한다.
- 위 발송 제한(번호·IP별) 외에 **서비스 전체 일일 발송 상한**을 둔다(제안: 200건/일, 구현 시 설정값). 상한에 닿으면 `SMS_UNAVAILABLE`로 응답하고 운영자에게 알린다.
- 재검토 기준: 월 발송 비용이 팀이 정한 금액을 넘거나, 일일 상한에 자주 닿거나, 공급자 장애가 반복될 때. 금액은 팀이 정해 이 ADR에 기록한다.
- **선결 조건(구현 시작 전)**: 공급자 계정과 결제 수단을 등록하고 관리할 사람을 정한다.

### 5. 개인정보

- 전화번호는 이미 필수로 수집하고 있어 새 수집 항목은 아니다. 다만 문자 발송 업체가 번호를 처리하므로 **개인정보 처리 위탁**을 개인정보처리방침과 동의 문구에 반영해야 한다(`/privacy-policy`는 아직 없다. 개발 일정의 미완 작업).
- 로그에는 전화번호를 마스킹해 남기고, 인증 코드는 로그에 남기지 않는다(개발 프로필의 로그 구현은 예외).
- 인증 이력(`phone_verification`)은 만료 후 일정 기간(제안: 7일)이 지나면 삭제한다.

## 검토한 대안

| 대안 | 장점 | 단점 | 결과 |
|---|---|---|---|
| 현행 유지(형식 검사만) | 비용 없음 | 계정 탈취 가능성이 남음 | 기각 |
| 이메일 인증으로 대체 | 비용 없음 | 이메일 계정 자체가 가입 정보라 재설정 본인 확인이 되지 않고, 50~60대 사용자에게 불편 | 기각 |
| 통신사 본인확인(휴대폰 본인인증 서비스) | 이름·생년월일까지 확인 | 건당 비용과 사업자 계약·심사 부담이 큼 (단가는 확인하지 못함) | 기각 (MVP 범위 초과) |
| 카카오 알림톡 | 도달률 높음 | 템플릿 심사가 필요하고 인증 용도 제약을 확인하지 못함 | 보류 |
| 소셜 로그인만 허용 | 번호 불필요 | 구글 계정이 없는 사용자를 배제 | 기각 |

## 영향

- **BE**: `phone_verification` 테이블, 발송·검증 API(`POST /api/auth/phone/send`, `POST /api/auth/phone/verify`), 인증 티켓 발급·검증, `register`·`reset-password`·`find-email`에 티켓 요구, 새 발송·검증 API를 `SecurityConfig`의 공개 경로에 추가(비로그인 상태에서 호출), `SmsSender`와 공급자 구현, 제한 로직
- **FE**: `RegisterPage`에 번호 인증 단계, 비밀번호 재설정·이메일 찾기 화면에 인증 단계, 재전송 타이머
- **DB**: `phone_verification` 생성 SQL을 `db/manual`에 추가 (운영은 `ddl-auto: validate`)
- **문서**: API 명세서(인증 섹션), 온보딩 플로우, 개인정보처리방침·동의 문구(위탁 고지), ADR-007에 이 ADR 연결 문구

## 결과와 남은 위험

- 재설정·찾기에 SMS 인증이 생기면 번호를 바꾼 기존 사용자는 스스로 복구할 수 없다. 운영자 문의 경로가 필요하다.
- 문자는 도달하지 않을 수 있다(통신사 지연, 해외 번호). 실패 시 재전송과 안내 문구가 필요하다.
- 단가·발신번호 등록 요건은 공식 문서로 확인하기 전까지 가정이다. 확인 결과에 따라 공급자 선택이 달라질 수 있다.
- Google 가입자는 번호가 없어 이번 ADR의 보호 범위 밖이다(비밀번호가 없는 계정이라 재설정 대상도 아니다).
