# ADR-014: 회원 탈퇴 정책 보완 (ADR-012 갱신)

## 상태

승인됨 (2026-11-02) — 아래 "확정한 항목"의 제안을 그대로 확정했다. 항목 1·2는 개인정보 관련 법률 검토 결과에 따라 바뀔 수 있고, 바뀌면 이 ADR을 갱신한다.

ADR-012의 처리 방식(이관 선택 + 역할별 처리)은 그대로 유지하고, 작성 이후 달라진 모델과 열려 있던 값을 보완한다. 충돌하는 부분은 이 ADR이 우선한다.

## 맥락

ADR-012(2026-10-22) 작성 뒤 다음이 바뀌었다.

- PR #184로 수정 제안(`record_suggestion`)과 기록 요청(`record_request`)이 제거됐다. ADR-012의 "제안 이력 익명화"는 대상이 없다.
- 활동지원사도 기록을 작성하고 본인 기록을 수정·삭제·복원한다(M7). ADR-012의 "작성한 기록은 익명 작성자로 유지"만으로는 익명화 뒤 그 기록을 누가 관리하는지 정해지지 않는다.
- 당사자 프로필에 주치의·병원, 활동지원센터 연락처 등 의료·연락처 정보가 추가됐다(ADR-013). 기관 이관 시 이 정보가 함께 넘어가는지 정해지지 않았다.
- 소프트 딜리트 유예 기간 N이 "7~30일 권장"으로만 남아 있다.
- 세컨드 보호자 `ACTIVE` 상태에서 주 보호자가 탈퇴하는 경우가 다뤄지지 않았다.

현재 코드에는 `DELETE /api/users/me`가 없다. `User`의 `email`은 필수·유니크이고 `googleId`가 있으며, `CareRecipient`에는 `deletedAt`이 없다.

## 확정한 항목

각 항목의 "제안"이 확정된 결정이다. 법률 검토 등으로 달라지면 이 ADR을 갱신한다.

### 1. 활동지원사·기관 탈퇴 뒤 그가 작성한 기록 — 제안: 보존하고 주 보호자가 삭제할 수 있다

- 기록은 당사자의 돌봄 연속성을 위한 데이터이므로 탈퇴로 지우지 않는다.
- 작성자 표시는 "탈퇴한 사용자"로 바꾼다.
- 작성자가 없으므로 수정은 막고, 주 보호자(세컨드 `ACTIVE` 포함)가 소프트 딜리트만 할 수 있다. 기존 "작성자 본인만 삭제" 규칙의 예외로, 익명화된 작성자의 기록에만 적용한다.

**검토한 대안**
- 탈퇴와 함께 작성 기록 삭제: 인수인계 정보가 사라져 서비스 목적과 어긋난다. 채택하지 않았다.
- 보존하되 아무도 수정·삭제 못 함: 틀린 기록을 바로잡을 방법이 없어 채택하지 않았다.

### 2. 기관 이관 시 의료·연락처 정보 — 제안: 이관 전에 비운다

- 이관 대상은 기록과 당사자 기본 정보다.
- 주치의·병원, 활동지원센터 연락처 등 ADR-013에서 추가한 의료·연락처 필드는 이관 전에 비운다. 의료 정보 동의(`sensitiveInfo`)의 주체인 보호자가 익명화되므로 동의 근거가 남지 않는다.
- 기관은 필요하면 새 보호자 또는 대리인에게서 다시 받는다.

**검토한 대안**
- 포함해서 이관: 돌봄 연속성은 높지만 동의 주체가 사라진 민감정보를 기관이 계속 보유한다. 법률 검토 없이는 채택하지 않았다.
- 별도 동의를 받고 이관: 탈퇴 흐름이 복잡해지고 보호자가 이미 떠나는 시점이라 현실적이지 않다.

### 3. 삭제 선택 시 유예 기간 — 제안: 30일

- 기록 복원 기한(삭제 후 30일 미만)과 같은 값으로 맞춰 사용자에게 설명하기 쉽게 한다.
- 유예 중에는 접근을 차단하고 복원을 허용한다. 30일이 지나면 하드 딜리트한다.

### 4. 세컨드 보호자가 있는 경우 — 제안: `ACTIVE`이면 승계한다

- 주 보호자 탈퇴 시 `ACTIVE` 세컨드 보호자가 있으면 주 보호자로 승격하고 당사자 데이터는 그대로 둔다. 이관/삭제 선택을 묻지 않는다.
- 세컨드가 초대 수락 전(`PENDING`)이거나 없으면 ADR-012대로 이관/삭제 선택을 강제한다. (코드의 `GuardianStatus`는 `ACTIVE`·`PENDING`·`REVOKED`이다. ERD 문서의 `INVITED`·`READY`는 코드와 다르다.)

## 결정 (ADR-012 유지 + 보완)

### 계정 익명화 규칙

탈퇴 시 `users` 행은 남기고 개인정보를 비운다. 행을 지우면 기록의 작성자 참조(`authorId` 등)가 깨지기 때문이다.

| 컬럼 | 처리 |
|---|---|
| `name` | "탈퇴한 사용자" |
| `email` | `deleted-{id}@deleted.invalid` (필수·유니크를 만족하는 자리표시자) |
| `phone` | null |
| `password` | null |
| `googleId` | null (같은 구글 계정으로 재가입할 수 있게 한다) |
| `publicCode` | 유지 (개인을 특정하지 않는 삶결 전용 식별자) |

- `users`에 탈퇴 시각 컬럼(`deletedAt`)을 추가해 탈퇴 계정을 구분한다. 운영은 `ddl-auto: validate`라 `db/manual`에 SQL을 추가한다.
- 활성 `refresh_tokens`는 모두 폐기한다. 이미 발급된 액세스 토큰(최대 15분)도 즉시 차단한다. 인증 필터가 요청마다 `users.deletedAt`을 기본 키로 조회해 탈퇴했거나 없는 계정이면 인증을 설정하지 않는다(401). 규모가 커지면 짧은 캐시를 얹는다.
- 같은 이메일로의 재가입은 허용한다(원래 이메일을 비웠으므로 충돌하지 않는다).

### 역할별 처리 (ADR-012 표 갱신)

| 시나리오 | 처리 |
|---|---|
| 주 보호자, `ACTIVE` 세컨드 있음 | 세컨드를 주 보호자로 승격, 계정 익명화 |
| 주 보호자, 세컨드 없음 | "기관 이관" 또는 "데이터 삭제" 선택 강제 |
| 이관 선택 | 의료·연락처 필드를 비우고 당사자 데이터를 연결된 모든 기관에 그대로 유지, 계정 익명화 |
| 삭제 선택 | 당사자와 연관 기록을 소프트 딜리트, 30일 뒤 하드 딜리트(S3 미디어 포함). 유예 중에는 보호자 연결을 철회하고 활성 배정을 종료하며 기관 연결을 거절 상태로 돌려 접근을 막는다(복원은 운영자가 되살린다) |
| 세컨드 보호자 탈퇴 | 계정 익명화만, 당사자 데이터 영향 없음 |
| 활동지원사 탈퇴 | 계정 익명화, 활성 배정 종료, 기관 소속 비활성화, 작성 기록은 보존(위 항목 1) |
| 기관 탈퇴 | 계정 익명화, 담당자 연결(`Organization.ownerId`)을 비우고 기관 코드를 재발급, 기관의 활성 배정 종료, 소속 지원사·기관-당사자 연결은 유지 (아래 "구현 전 확정한 세부" 2) |
| 연결된 기관이 없는 보호자가 이관 선택 | "연결된 기관이 없습니다" 안내 후 삭제만 허용 (ADR-012 유지) |

- 이관 시 기관 담당자에게 알림을 보낸다 (ADR-012 유지).
- 접근 이력(`access_log`)은 감사 목적으로 보존하되 행위자는 익명화된 계정을 가리킨다. 보관 기간은 법률 검토에서 확인한다.
- `CareRecipient`에 `deletedAt` 컬럼을 추가해 소프트 딜리트를 구현한다.

### 구현 전 확정한 세부 (2026-11-02)

구현 이슈를 만들기 전에 승인 뒤 드러난 네 가지 빈틈을 확정했다.

**1. 여러 기관에 연결된 당사자의 "이관"**

- 기관-당사자 연결은 (기관, 당사자) 쌍 단위라 한 당사자가 여러 기관에 연결될 수 있다.
- 이관은 새 기관에 넘기는 일이 아니라 **보호자 개인정보를 익명화하고 당사자 데이터를 지우지 않고 유지하는 것**으로 정의한다. 연결된 모든 기관이 기존 접근 권한 그대로 계속 접근하며, 이관 대상 기관을 고르는 화면은 만들지 않는다. 접근 범위가 넓어지지 않는다.
- 이관 알림은 연결된 모든 기관 담당자에게 보낸다.

**2. 기관 계정 탈퇴**

- 탈퇴를 허용한다. 계정은 익명화하고 `Organization.ownerId`를 null로 되돌린다. ADR-010에서 `ownerId`를 nullable로 둔 구조라서 새 담당자가 기관 코드로 기관을 다시 인수할 수 있다.
- **기관 코드는 탈퇴 때 재발급한다.** 기관 코드는 QR로 보호자·지원사에게 공유되는데, 담당자 없는 기관은 코드만으로 어떤 기관 계정이든 인수할 수 있다(`OrganizationService.register`). 그대로 두면 코드를 아는 누구든 연결된 모든 당사자의 기록에 접근한다. 코드를 바꿔 이전 코드를 무효화하고, 슈퍼 어드민이 새 코드를 후임 담당자에게 전달한다. 후임이 같은 기관을 이어받는 구조와 소속 지원사·당사자 연결은 그대로다. 기존에 인쇄한 QR은 다시 인쇄해야 한다.
- 기관의 **활성 배정은 종료**한다. "담당 종료 시 즉시 접근 회수" 원칙에 따라, 담당자 없이 지원사가 당사자 정보에 계속 접근하지 않게 한다.
- 소속 지원사(`organization_member`)와 기관-당사자 연결은 유지한다.
- 탈퇴 전에 "활성 배정 N건이 종료됩니다"를 경고한다. 새 담당자가 인수한 뒤 배정을 다시 만들어야 하고 그동안 돌봄이 끊길 수 있다는 점을 감수한다.

**3. 당사자가 여러 명인 보호자**

- 탈퇴는 계정 단위이지만 이관/삭제는 **당사자별로** 고른다. 당사자마다 `ACTIVE` 세컨드 유무, 연결된 기관 유무가 달라 일괄 선택으로는 담을 수 없다.
  - `ACTIVE` 세컨드가 있는 당사자: 자동 승계, 선택 없음
  - 연결된 기관이 없는 당사자: 삭제만 가능
  - 그 외: 이관/삭제 중 선택. 삭제를 실수로 누르지 않도록 **기본값은 비워** 직접 고르게 한다
- 탈퇴 전 미리보기 API로 당사자별 선택 가능 여부를 조회한다. `DELETE /api/users/me`는 당사자별 결정 목록을 받고, 선택이 필요한 당사자의 결정이 하나라도 없으면 422로 거부한다.
- 전체 처리는 한 트랜잭션으로 묶어 일부만 반영되지 않게 한다.
- 화면은 당사자 카드를 나열하고 선택이 필요한 카드에만 라디오를 보여 준다 (ADR-002의 "한 화면 한 정보").
- "모두 이관", "모두 삭제" 일괄 버튼은 처음에는 만들지 않는다.

**4. 이관된 당사자의 재연결**

- 이관된 당사자는 주 보호자가 없다. 그대로 두면 `claim`이 당사자 고유 코드만으로 보호자를 연결하므로, 코드를 아는 보호자 계정이 승인 없이 기록·프로필에 접근할 수 있다.
- **기관 승인 방식**으로 막는다. 이관된 당사자에 표시(`care_recipient.transferred_at`)를 두고, 표시가 있는 당사자를 `claim`하면 즉시 연결하지 않고 `PENDING`(주 보호자)으로 만든다. 연결된(`ACCEPTED`) 기관 중 한 곳의 담당자가 승인하면 `ACTIVE`가 된다.
- `PENDING` 상태에서는 접근할 수 없다. 대기 요청은 30일 뒤 만료한다. 기관 담당자가 없으면 새 담당자가 인수할 때까지 대기한다.
- 표시가 없는 당사자(어드민이 사전 발급한 코드, ADR-011)는 지금처럼 바로 연결된다.
- 이관은 `ACCEPTED` 기관이 있을 때만 가능하므로 승인 주체가 항상 존재한다.
- 현재 `PENDING`은 세컨드 보호자 초대에만 쓰인다. 구현 시 `claim`의 중복 검사, 접근 차단, 승인·거절 처리, 기관 홈의 "보호자 연결 요청" 화면을 함께 고친다.
- 이관의 대상이 되는 "연결된 기관"은 `ACCEPTED` 상태만이다. 승인 대기(`PENDING`) 요청은 이관 알림과 계속 접근의 대상이 아니다.
- 주 보호자가 없는 동안 프로필·루틴은 보호자만 수정할 수 있으므로 사실상 읽기 전용이 된다. 의도된 동작이다.

**검토한 대안**: 코드만으로 연결하는 현행 유지(코드 유출 시 곧바로 접근, 막을 사람이 없음), 기관이 새 코드를 발급해 기존 코드를 무효화(고유번호는 기관이 당사자를 찾는 식별자라 바꾸면 인수인계가 혼란스러워짐).

### 하지 않는 것

- 탈퇴 취소(복구): 계정 익명화는 되돌릴 수 없다. 복원은 당사자 삭제 유예 중의 데이터에만 해당한다.
- 이관 대상 기관을 보호자가 탈퇴 화면에서 고르는 기능: 연결된 모든 기관에 유지한다.

## 영향

- **BE**: 탈퇴 미리보기 API(당사자별 선택 가능 여부), `DELETE /api/users/me`(당사자별 결정 목록), 계정 익명화, 세컨드 승계, 이관 시 필드 비우기, 소프트 딜리트 후 하드 딜리트 스케줄러, 익명 작성자 기록의 삭제 권한 예외
- **FE**: 기관 홈의 "보호자 연결 요청" 승인 화면, `MorePage`에 탈퇴 진입점, 세컨드 유무에 따른 이관/삭제 선택 다이얼로그, 기록 목록의 "탈퇴한 사용자" 표기
- **DB**: `users.deletedAt`, `care_recipient.deletedAt`, `care_recipient.transferred_at` 컬럼 추가 SQL(`db/manual`)
- **문서**: API 명세서의 `DELETE /api/users/me`(현재 "파기 정책 미정" 계열 표기), 마이페이지 플로우

## 결과와 남은 위험

- 정책 1(기록 보존)과 2(의료 정보 비움)는 개인정보 처리 근거에 대한 법률 검토가 필요하다. K-startup 전문가 상담(#74)과 함께 확인한다.
- 이관 시 의료 정보를 비우면 기관이 일부 정보를 다시 모아야 한다. 현장 반응을 보고 재검토한다.
- 계정 익명화는 되돌릴 수 없으므로 탈퇴 화면에서 2단계 확인을 둔다 (ADR-002 파생 원칙 3).
