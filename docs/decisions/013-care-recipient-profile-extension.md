# ADR-013: 당사자 프로필 확장 데이터 모델과 의료 정보 동의 방식

## 상태

승인됨

## 맥락

이슈 #197에서 당사자 프로필에 주치의·병원, 활동지원센터, 루틴을 추가하고 장애 정도 표기를 "심한 장애 / 심하지 않은 장애"로 바꾼다. 스키마 변경은 운영 DB(`ddl-auto: validate`)에서 되돌리기 어려워 저장 구조와 동의 방식을 먼저 결정한다.

## 결정

### 1. 주치의·병원, 활동지원센터: 당사자 테이블 컬럼

- 당사자당 각각 1개만 받는다.
- `care_recipient`에 nullable 컬럼으로 추가한다 (주치의명, 병원명, 병원 연락처, 활동지원센터명, 센터 연락처 등. 세부 필드는 구현 시 확정).
- 활동지원센터는 자유 입력이며 기관 계정(코드 기반 연결, ADR-010)과 연동하지 않는다.

**검토한 대안**: 별도 테이블로 여러 건을 받는 방식. 현재 요구는 1개이고 조인·마이그레이션 비용이 커서 채택하지 않았다. 여러 건이 필요해지면 그때 분리한다.

### 2. 루틴: 별도 테이블

- `care_recipient_routine(id, care_recipient_id, time, title, memo)`로 당사자와 1:N 관계를 둔다.
- 시간은 `HH:mm`, 제목은 필수, 메모는 선택이다.
- 반복 요일, 알림, 수행 체크 기록은 범위에서 제외한다.
- 조회·수정 권한은 기존 당사자 프로필의 역할별 접근 제어(`CareAccessService`)를 따른다.

**검토한 대안**: `care_recipient`에 JSON 컬럼으로 저장하는 방식. 항목 단위 수정·삭제와 정렬이 어렵고, 개발(H2)·운영(MySQL) 간 JSON 지원 차이가 있어 채택하지 않았다.

### 3. 장애 정도: 두 구분 enum

- `Integer disabilityGrade`를 `DisabilitySeverity { SEVERE, NOT_SEVERE }`로 대체한다.
- 기존 데이터는 1~3급 → `SEVERE`, 4급 이상 → `NOT_SEVERE`, 값 없음 → null로 변환한다.
- 변환 SQL은 `backend/src/main/resources/db/manual/`에 추가한다.

### 4. 의료 정보 동의: 기존 `sensitiveInfo` 항목 문구 보강

- 보호자 동의 화면의 기존 필수 항목 "건강·복약정보 등 민감정보 처리 동의"(`sensitiveInfo`)에 주치의·병원 정보를 명시한다.
- 문구를 바꾸므로 `termsVersion`을 올린다.
- `Consent` 엔티티, 동의 요청 DTO, 동의 티켓(JWT) 구조는 바꾸지 않는다.

**검토한 대안**: 의료 정보 전용 동의 필드를 신설하는 방식. `Consent`, 동의 티켓, 인증 서비스, 관리자 서비스, 시드 데이터, 테스트, 마이그레이션까지 영향이 크고 기존 가입자의 재동의 처리가 필요해 채택하지 않았다.

## 결과와 남은 위험

- 기존 가입자는 이전 `termsVersion`으로 동의한 상태로 남는다. 재동의를 받을지는 별도로 결정한다.
- 동의 항목을 분리해서 받아야 한다는 법적 판단이 나오면 신설 방식으로 전환하며, 이때는 별도 ADR을 작성한다.
- 기존 급수에서 두 구분으로 변환할 때 원래 급수 정보는 사라진다. 운영 DB 적용 전에 백업한다.
