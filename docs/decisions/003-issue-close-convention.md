# ADR-003: 이슈 종료 컨벤션 — Refs vs Closes

**상태:** 채택

---

## 배경

GitHub은 커밋 메시지나 PR 본문에서 `Closes #번호` 키워드를 감지해 PR이 기본 브랜치에 병합될 때 해당 이슈를 자동 종료한다.

삶결 프로젝트는 `develop`을 통합 브랜치로 사용하고 `main`이 기본(기본) 브랜치다. 따라서 `Closes`는 `develop → main` 병합 시에만 자동 종료 효과를 가지며, `develop` 병합만으로는 동작하지 않는다.

---

## 고려한 옵션

### 옵션 1: 모든 PR에 `Closes` 사용

**장점:** GitHub 자동 종료로 수동 작업 없음

**단점:**
- `develop` 병합 시 이슈가 종료되지 않음에도 `Closes`를 쓰면 의미가 오해됨
- 배포가 완료 기준인 이슈를 `main` 병합 시 자동 종료하면 검증 전에 닫힘

→ **기각**: 실제 종료 시점과 키워드 의미가 불일치

### 옵션 2: 모든 PR에 `Refs` 사용 — 수동 종료 전용

**장점:** 종료 기준을 담당자가 완전히 제어

**단점:**
- `develop → main` 릴리즈 PR에서도 자동 종료를 쓸 수 있는 경우에도 수동으로만 가능
- 수동 종료를 잊으면 이슈가 영구 Open 상태로 방치됨

→ **부분 채택**: develop 대상 PR의 기본값으로 사용

### 옵션 3: 대상 브랜치에 따라 구분 ✅ 채택

| PR 대상 | 키워드 | 이유 |
|---------|--------|------|
| `develop` | `Refs #번호` | 기본 브랜치 병합 아님 → 자동 종료 없음. 수동 종료 기준 유지 |
| `develop → main` (릴리즈) | `Closes #번호` (권장) 또는 `Refs #번호` | 배포가 완료 기준인 이슈는 `Refs` 유지 후 배포 검증 후 수동 종료 |

---

## 결정

**옵션 3 채택**: develop 대상은 `Refs`, 릴리즈 PR은 `Closes` 권장.

이유:
1. **명확한 완료 기준**: `develop` 병합 ≠ 완료. 배포·검증이 완료 기준인 이슈가 많음
2. **자동 종료의 선택적 활용**: 릴리즈 PR에서 이슈 완료 = 배포 완료인 경우 `Closes`로 자동 종료 가능
3. **예외 처리**: 배포가 완료 기준인 이슈는 담당자가 `Refs`를 명시하고 배포 검증 후 수동 종료

---

## 구현 규칙

- 일반 커밋·`develop` 대상 PR: `Refs #번호`
- `develop → main` 릴리즈 PR: `Closes #번호` (배포 완료 = 이슈 완료인 경우) 또는 `Refs #번호` (배포 별도 검증 필요한 경우)
- 어느 경우든 마지막 PR 병합 후 담당자가 완료 기준과 검증 결과를 확인하고 수동 종료
