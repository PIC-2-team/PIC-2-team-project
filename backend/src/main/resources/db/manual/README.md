# 운영 DB 수동 SQL

운영은 `ddl-auto: validate`라서 엔티티가 쓰는 테이블·컬럼이 운영 DB에 없으면 **서버가 기동하지 못한다**. 스키마를 바꾸는 PR은 이 폴더에 SQL을 추가하고, 배포 전에 운영 DB에 직접 적용한다. 개발(H2)과 로컬은 자동으로 만들어지므로 이 SQL이 필요 없다.

## 적용 방법

1. 배포하려는 릴리즈에 포함된 SQL을 확인한다(릴리즈 PR의 변경 파일에서 이 폴더를 본다)
2. **서버를 배포하기 전에** 운영 DB에 번호 순서로 적용한다. 새 서버는 컬럼이 없으면 기동하지 못한다
3. 적용한 파일 이름을 릴리즈 노트(릴리즈 PR 본문)에 기록한다. 이 저장소에는 적용 이력을 남기는 곳이 없다. 운영 DB에 어떤 번호까지 적용됐는지는 이 문서에서 알 수 없으므로 운영 DB에서 확인해야 한다
4. 파일 첫 주석을 먼저 읽는다. 중복 데이터를 지우는 SQL(005, 006)은 백업 테이블을 먼저 만들고 결과를 확인한 뒤 백업을 직접 지우라고 안내한다. 같은 SQL을 두 번 실행하면 `ADD COLUMN`에서 실패하는 파일이 있다

## 새 SQL 번호 정하기

1. 작성 직전에 최신 `develop`을 받고 이 폴더에서 **가장 큰 번호 + 1**을 쓴다. 지금 다음 번호는 `014`다
2. 파일 이름은 `NNN-짧은-영문-설명.sql`이고, 첫 주석에 무엇을 하는지와 관련 이슈·ADR, 재실행 가능 여부를 적는다
3. 병합 전에 `develop`을 다시 합치고 같은 번호가 생겼는지 확인한다. 나중에 병합하는 PR이 번호를 바꾼다
4. 병합된 파일의 이름과 내용은 바꾸지 않는다. 운영에서 이미 적용했거나 노트에 인용됐을 수 있다

## 번호가 겹친 파일

009와 012가 겹쳤다. 병렬로 열린 PR이 같은 번호를 골랐기 때문이다. 파일 이름은 이미 노트와 PR에서 인용되고 있어 바꾸지 않았다. 이름을 바꿀지는 팀이 정하면 별도 작업으로 한다. 위 번호 규칙(3번)이 같은 일을 막는다.
