# PR 셀프 리뷰 (삶결 팀)

이 스킬은 팀원이 개인 환경에 별도 리뷰 스킬이나 에이전트를 설치하지 않아도 따라 할 수 있어야 한다. 아래 절차를 기본 방법으로 사용하고, 보조 도구는 팀 환경에서 사용할 수 있을 때만 선택적으로 활용한다.

## 실행 방법

```text
/self-review                         # 현재 브랜치 PR을 찾고, 없으면 로컬 리뷰
/self-review <PR 번호 또는 URL>      # 지정한 PR 리뷰
/self-review --base main             # PR 없는 릴리즈 후보의 로컬 리뷰
```

- PR 번호나 URL이 있으면 지정된 PR을 검토한다.
- 인자 없이 실행하면 현재 브랜치에 연결된 PR을 찾는다. PR이 없으면 로컬 리뷰로 전환하고 기본 비교 기준은 `develop`이다.
- `develop → main` PR은 `main`을 기준으로 검토한다. 릴리즈 후보를 로컬에서 검토할 때는 `--base main`을 지정한다.
- GitHub 조회가 실패하면 오류와 로컬 리뷰 가능 여부를 구분해 알린다. PR을 임의로 만들지 않는다.
- 실행 결과를 먼저 사용자에게 보여준다. 리뷰 게시와 코드 수정은 각각 승인된 범위에서만 수행한다.

## 작업 원칙

- 저장소의 `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`와 변경 경로의 추가 지침을 읽는다.
- 리뷰 → 결과 게시 → 수정 승인 → 수정·검증 → 완료 게시 순서로 진행한다. 문제가 없으면 수정 단계를 건너뛴다.
- 리뷰 요청만으로 GitHub 게시나 코드 수정 승인을 가정하지 않는다. 게시 내용과 대상을 제시하고 승인받되, 이미 승인된 범위는 다시 묻지 않는다.
- PR 생성·리뷰어 지정·Ready 전환·병합은 별도 승인 범위에서만 수행한다. 셀프 리뷰는 팀원의 Approve를 대신하지 않는다.
- 기존 변경을 보존하고, 시크릿·개인정보를 리뷰 본문에 복사하지 않는다.

## 1. 대상과 diff 확인

저장소 루트에서 다음 정보를 확인한다.

```bash
git status --short --branch
git branch --show-current
gh repo view --json nameWithOwner
gh pr view --json number,url,title,body,baseRefName,headRefName,headRefOid,isDraft
```

사용자가 PR을 지정했다면 `gh pr view <번호 또는 URL>`과 이후 명령에 같은 대상을 사용한다. 일반 PR의 기준 브랜치는 `develop`, `develop → main` 릴리즈의 기준 브랜치는 `main`이다.

PR이 있으면 GitHub의 실제 diff와 로컬 정보를 함께 확인한다.

```bash
gh pr diff <PR번호>
git fetch origin <base>
git rev-list --count origin/<base>..HEAD
git diff --stat origin/<base>...HEAD
git diff origin/<base>...HEAD
git log --oneline --graph origin/<base>...HEAD
git merge-base origin/<base> HEAD
```

- 로컬 HEAD와 PR의 `headRefOid`가 다르거나 로컬에 미커밋 변경이 있으면, 게시된 PR과 로컬 상태의 결과를 분리한다. 다른 브랜치에서 실행한 테스트를 PR 검증으로 기록하지 않는다.
- PR 리뷰에서는 미커밋·미추적 파일을 PR diff에 섞지 않고 별도 표시한다.
- 로컬 전용 리뷰에서는 지정한 base와 작업 트리를 비교한다.

```bash
git diff --name-only origin/<base>
git diff origin/<base>
git status --short
git diff --cached
git diff
```

미추적 파일은 diff에 자동 포함되지 않으므로 `git status --short`에서 확인한 뒤 내용을 직접 읽는다.

커밋이 있다는 사실만으로 `develop`에서 분기했다고 단정하지 않는다. merge-base와 커밋 그래프를 확인하고, 생성 당시 분기점을 증명할 수 없으면 `확인 필요`로 표시한다. 기준 브랜치의 최신 커밋을 포함하지 않는다는 이유만으로 잘못된 분기라고 하지 않는다. fetch에 실패하면 오래된 로컬 ref를 썼다는 한계를 남긴다.

## 2. PR 템플릿 검사

PR base에 맞는 실제 템플릿을 읽고 PR 본문과 대조한다. 경로와 항목별 상태·근거를 결과에 기록한다.

| PR 종류 | 템플릿 경로 |
|---|---|
| 일반 PR (`develop` 대상) | `.github/PULL_REQUEST_TEMPLATE/default.md` |
| 릴리즈 PR (`develop → main`) | `.github/PULL_REQUEST_TEMPLATE/release.md` |

HTML 주석, 안내 문구, 예시, 빈 목록 항목, 바꾸지 않은 플레이스홀더는 작성된 내용으로 세지 않는다. 필수 항목이 비어 있거나 예시가 남아 있으면 미작성이다. `리뷰어에게`처럼 선택 항목으로 안내된 부분은 비어 있어도 오류가 아니다.

| 항목 | 기준 |
|---|---|
| PR 제목 | `타입: 한 줄 요약`, 50자 이내 |
| 연관 이슈 | 일반 PR은 `Refs #번호` 또는 `없음`. 릴리즈는 `Closes #번호` 규칙 적용 |
| 변경 목적 | 해결할 문제와 변경 이유가 구체적으로 작성됨 |
| 변경 사항 | 실제 diff와 일치함. 릴리즈는 포함 PR과 릴리즈 메모 확인 |
| 검증 | 체크된 항목은 실제 결과가 있음. 미실행은 이유와 남은 위험 기록 |
| 템플릿 | `develop` 대상은 `default`, `develop → main`은 `release` |
| 시크릿 | 자격증명·비밀번호·비밀 환경 파일이 변경에 포함되지 않음 |
| 브랜치 기반 | 대상 브랜치와 비교한 Git 근거. 근거 부족은 `확인 필요` |

PR이 없으면 템플릿 검사는 `미확인`으로 두고 코드 리뷰 결과만 제공한다.

## 3. 코드 품질 검사

다음 순서로 진행한다.

1. **목적과 기대 동작 확인:** PR·이슈·요청에서 바뀌는 동작을 한두 문장으로 정리한다. 요구사항이 모호하면 확인된 내용과 불명확한 부분을 나눈다.
2. **테스트 먼저 읽기:** 정상·경계·실패 사례를 확인한다. 테스트가 없거나 실제 동작을 충분히 검증하지 못하면 놓치는 동작을 기록한다. 테스트 부재만으로 심각한 결함이라고 단정하지 않는다.
3. **변경 흐름 따라가기:** 전체 diff, 변경 파일 전체, 호출부와 관련 테스트를 읽는다. 요청 진입부터 입력 검증·권한 확인·상태 변경·저장·응답까지 추적하고, 외부 API·DB 실패 시 동작도 확인한다.
4. **변경 영향에 맞춰 아래 질문을 확인한다.** 해당 없는 항목은 문제를 만들지 말고 `해당 없음`으로 둔다.

| 관점 | 확인 질문 |
|---|---|
| 정확성 | 요구한 동작을 하는가? 빈 값·누락 값·경계값·잘못된 입력, 실패·재시도·중복 실행에서 결과와 상태가 올바른가? 기존 동작에 회귀가 없는가? |
| 테스트 | 핵심 동작과 실패·경계 사례를 확인하는가? 구현 세부사항에만 결합되거나 회귀를 놓치는 테스트는 아닌가? |
| 가독성·단순성 | 이름과 흐름만으로 의도가 보이는가? 불필요한 중복·복잡성·추상화를 추가하지 않았는가? 기존 관례와 맞는가? |
| 구조 | 모듈 책임과 경계가 자연스러운가? 의존 방향이 적절한가? 기존 코드와 중복되거나 충돌하지 않는가? |
| 보안·개인정보 | 입력과 외부 데이터를 사용 전에 검증하는가? 인증뿐 아니라 리소스 권한을 확인하는가? 민감정보가 응답·로그에 노출되지 않는가? SQL·명령·HTML 입력이 안전하게 처리되는가? |
| 성능 | 쿼리·네트워크 호출이 항목마다 반복되지 않는가? 무제한 조회·반복 또는 큰 작업이 추가되지 않았는가? UI에서 불필요한 재렌더링이나 큰 초기 로드가 생기지 않는가? |
| UI·접근성 (UI 변경 시) | 로딩·빈 결과·오류·성공 상태가 있는가? 작은 화면·키보드·스크린리더에서 사용할 수 있는가? |
| 데이터 (저장 구조 변경 시) | 기존 데이터와 호환되는가? 제약·기본값·마이그레이션 영향이 확인되었는가? |

5. **검증 결과 대조:** 변경에 맞는 테스트·정적 검사·빌드·브라우저 확인 결과가 해당 PR 커밋에서 나온 것인지 확인한다. 실행하지 못했다면 이유와 남은 위험을 기록한다.
6. **지적 검증:** 각 후보의 코드 위치와 실행 경로를 다시 확인해 조건·기대 동작·실제 영향을 입증한다. 근거가 부족하면 결함으로 쓰지 않고 `확인 필요`나 검토 한계로 분리한다.

### 검증 명령

변경 파일에 가까운 테스트를 먼저 실행한다. 공통 모듈·인증·권한·데이터 흐름처럼 영향이 넓으면 해당 영역 전체 검증도 실행한다.

| 변경 경로 | 명령 |
|---|---|
| 프론트엔드 특정 테스트 | `cd frontend && npm test -- src/path/Feature.test.tsx` |
| 프론트엔드 전체 테스트 | `cd frontend && npm test` |
| 프론트엔드 정적 검사·빌드 | `cd frontend && npm run lint && npm run build` |
| 백엔드 특정 테스트 클래스 | `cd backend && ./gradlew test --tests 'com.project.backend.FeatureTest'` |
| 백엔드 전체 테스트 | `cd backend && ./gradlew test` |
| FE·BE 통합 변경 | 해당 영역별 테스트와 정적 검사·빌드 |
| 브라우저 동작 확인이 필요한 UI 변경 | `cd frontend && npm run test:e2e` 또는 화면 수동 확인 |

저장소 CI가 다른 명령을 사용하면 workflow를 확인하고 CI 결과와 로컬 결과를 구분한다. 명령이 실패하면 원인을 확인하고, 실행할 수 없으면 미실행 이유를 쓴다. 성능 문제는 측정값이나 구체적인 쿼리·알고리즘 근거 없이 추측으로 보고하지 않는다. 별도 리뷰 스킬이나 에이전트는 팀 환경에서 제공될 때만 선택 사항으로 쓴다. 이 절차는 보조 도구 없이도 완료할 수 있어야 한다.

### 지적 심각도와 판정

| 심각도 | 기준 | 처리 |
|---|---|---|
| **Critical** | 보안 침해, 데이터 손실, 핵심 기능 중단 등 병합 시 중대한 피해 | 리뷰 요청 전에 수정 |
| **Important** | 재현 가능한 기능 오류·회귀 또는 요구사항 누락으로 잘못된 결과 발생 | 리뷰 요청 전에 수정. 예외 진행은 명시적 승인과 위험 기록이 필요하며 자동 통과 판정하지 않음 |
| **Suggestion** | 결함은 아니지만 가독성·구조·성능 개선 여지가 있음 | 선택 사항. 리뷰 요청을 막지 않음 |

각 결함에는 심각도, 파일·줄, 발생 조건 또는 재현 단계, 기대 동작과 실제 영향, 근거, 수정 방향을 적는다. 같은 원인의 지적은 합친다.

- 미해결 `Critical` 또는 `Important`가 있으면 `❌ 수정 필요`다.
- 해당 지적이 없고 필수 검증·근거가 갖춰지면 `✅ 리뷰 요청 가능`이다. `Suggestion`은 판정을 막지 않는다.
- 검증을 못 했거나 대상 SHA·요구사항·근거가 불명확하면 `확인 필요`다.
- 사용자가 미해결 위험을 수용해도 이를 기록하고 자동으로 `✅` 처리하지 않는다.

## 4. 결과 작성 및 게시

결과를 먼저 사용자에게 보여준다.

```text
## 셀프 리뷰 결과 (`/self-review`)

브랜치: <head> → <base> | 커밋: <개수>
검토 대상: <PR 번호·URL 또는 로컬 리뷰>
검토 시점: PR head SHA <sha 또는 해당 없음> | 로컬 HEAD SHA <sha>
미커밋 변경: <포함 여부와 파일 또는 없음>

### 템플릿
- 경로: <실제 템플릿 경로 또는 미확인>
- ✅ / ❌ / 확인 필요: <항목 — 근거>

### 코드 품질
- <심각도, 파일·줄, 재현 조건, 근거, 영향, 수정 방향>
- <발견 사항이 없으면 검토 범위와 한계>

### 검증
- <실행 명령과 결과 또는 미실행 이유·남은 위험>

### 판정
<✅ 리뷰 요청 가능 / ❌ 수정 필요 / 확인 필요>
```

필수 검증이나 근거가 부족하면 `✅`로 판정하지 않는다. PR이 없거나 게시 승인을 받지 못하면 초안만 전달한다.

게시 승인을 받은 경우, 게시 직전에 PR 번호·저장소와 최신 `headRefOid`를 다시 확인한다. 검토한 SHA와 달라졌으면 게시를 멈추고 새 diff를 검토한 뒤 결과와 승인을 갱신한다. 결과가 승인된 내용과 같을 때만 COMMENT 리뷰를 게시한다.

```bash
gh pr review <PR번호> --repo <owner/repo> --comment --body-file <리뷰본문파일>
```

본문은 승인된 내용 그대로 임시 파일에 작성한다. 셸 문자열에 본문을 직접 넣지 않는다. 성공 여부를 확인하고 실패하면 게시 완료라고 보고하지 않는다.

## 5. 수정 승인과 반영

수정이 필요하면 현재 상태와 제안 수정·범위를 사용자에게 제시하고 명시적으로 승인받는다. 승인된 항목만 수정하고 관련 검증과 diff 검토를 다시 수행한다.

검증을 통과하면 수정 파일만 명시적으로 stage하고 실제 변경을 설명하는 커밋을 만든다. `git add .`는 사용하지 않는다. 저장소 지침과 승인된 범위에 따라 push한다. `main`·`develop` 직접 push, force push, 브랜치 삭제는 하지 않는다. 검증 실패·미완료 상태는 커밋·push하지 않는다.

수정 후 수정 내용·커밋·검증 결과·남은 문제를 포함한 완료 코멘트 초안을 작성한다. 승인된 게시 범위에 따라 등록하며, 미해결 항목이 있으면 완료나 리뷰 가능으로 표시하지 않는다.

리뷰어는 `develop` 대상에서 상대 팀원 1명, `develop → main`에서 FE·BE 담당자 모두가 필요하다. 실제 지정이나 Ready 전환을 수행하지 않았다면 완료했다고 쓰지 않는다.
