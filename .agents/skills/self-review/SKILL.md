# PR 셀프 리뷰 (Codex)

저장소 안에서 `$self-review`로 호출한다. 기존 `.claude/skills/self-review/SKILL.md`의 리뷰 흐름을 Codex용으로 적용한 스킬이다.

## 실행 방법

```text
$self-review                         # 현재 브랜치의 PR을 찾고, 없으면 로컬 리뷰
$self-review <PR 번호 또는 URL>      # 지정한 PR 리뷰
$self-review --base main             # PR이 없는 릴리즈 후보의 로컬 리뷰
```

- PR 번호나 URL을 지정하면 해당 PR을 검토한다. 로컬 브랜치가 PR head와 다르면 게시된 PR과 로컬 작업물을 구분해 보고한다.
- 인자 없이 실행하면 현재 브랜치에 연결된 PR을 조회한다. PR이 없으면 로컬 리뷰로 전환하고, 기본 비교 기준은 `develop`이다. 릴리즈 로컬 리뷰는 `--base main`을 사용한다.
- 지정한 PR을 찾을 수 없거나 GitHub 조회가 실패하면 원인을 구분한다. PR을 임의로 만들지 않고 가능한 로컬 리뷰만 수행한다.
- 모든 모드에서 리뷰 결과를 먼저 작성한다. GitHub 게시와 코드 수정은 각각 승인된 범위에서만 한다.

## 작업 원칙

- 저장소의 `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`와 변경 경로의 추가 지침을 읽는다.
- 리뷰 → 결과 게시 → 수정 승인 → 수정·검증 → 완료 게시 순서로 진행한다. 문제가 없으면 수정 단계는 생략한다.
- 리뷰 요청만으로 GitHub 게시나 코드 수정 권한을 가정하지 않는다. 게시할 내용과 대상을 먼저 제시하고 승인을 받되, 이미 명시적으로 승인된 범위는 재확인하지 않는다.
- PR 생성·리뷰어 지정·Ready 전환·병합은 별도 승인 범위에서만 수행한다. 셀프 리뷰는 팀원의 Approve를 대신하지 않는다.
- 사용자의 기존 변경을 보존하고 시크릿·개인정보를 리뷰 본문에 복사하지 않는다.

## 1. 대상과 diff 확인

저장소 루트에서 현재 상태를 확인한다.

```bash
git status --short --branch
git branch --show-current
gh repo view --json nameWithOwner
gh pr view --json number,url,title,body,baseRefName,headRefName,headRefOid,isDraft
```

사용자가 PR 번호나 URL을 지정했다면 `gh pr view`와 이후 PR 명령에 해당 대상을 명시한다. PR이 없거나 GitHub 접근이 실패하면 이유를 구분해 보고하고, 가능한 로컬 리뷰를 진행한다. PR을 임의 생성하지 않는다.

일반 리뷰의 base는 `develop`이다. PR의 실제 base가 다르면 이를 알리고 대상에 맞춰 검토한다. `develop → main`은 릴리즈 템플릿과 FE·BE 양쪽 리뷰 요건을 적용한다.

```bash
git fetch origin develop
git rev-list --count origin/develop..HEAD
git diff --stat origin/develop...HEAD
git diff origin/develop...HEAD
git log --oneline --graph origin/develop...HEAD
git merge-base origin/develop HEAD
```

릴리즈 리뷰라면 위 비교 기준을 `origin/main`으로 바꾸고 해당 ref를 fetch한다. fetch 실패 시 오래된 로컬 ref를 사용한다는 한계를 명시한다.

PR이 있으면 `gh pr diff <PR번호>`를 함께 확인한다. 로컬 HEAD와 PR의 `headRefOid`가 다르거나 미커밋 변경이 있으면 로컬 검사와 게시된 PR 검사를 구분한다. PR 모드의 미커밋·미추적 파일은 PR diff에 포함하지 않고 별도 표시한다. 로컬 전용 모드는 지정 base와 작업 트리의 tracked diff를 검토하고, 미추적 파일은 상태 목록에 표시한 뒤 파일 내용을 별도 확인한다. 다른 브랜치에서 실행한 테스트를 PR 검증 결과로 사용하지 않는다.

커밋이 존재한다는 사실만으로 develop에서 분기했다고 판정하지 않는다. merge-base, 커밋 그래프와 필요시 reflog를 확인하되, 생성 당시 기준 브랜치를 증명할 수 없으면 `확인 필요`로 표시한다. develop의 최신 커밋을 포함하지 않는다는 이유만으로 잘못된 분기라고 단정하지 않는다.

## 2. 템플릿 검사

PR base에 맞는 실제 템플릿을 읽고 PR 본문과 대조한다. 경로는 결과에 기록한다.

| PR 종류 | 템플릿 경로 |
|---|---|
| 일반 PR (`develop` 대상) | `.github/PULL_REQUEST_TEMPLATE/default.md` |
| 릴리즈 PR (`develop → main`) | `.github/PULL_REQUEST_TEMPLATE/release.md` |

HTML 주석, 안내 문구, 예시, 빈 목록 항목, 바꾸지 않은 플레이스홀더는 작성된 내용으로 세지 않는다. 해당 템플릿의 필수 항목마다 실제 내용을 확인하고, 비어 있거나 템플릿 예시가 남아 있으면 미작성으로 판정한다. `리뷰어에게`처럼 템플릿에서 선택 사항으로 명시한 항목은 비어 있어도 미작성 오류로 판정하지 않는다.

| 항목 | 기준 |
|---|---|
| PR 제목 | `타입: 한 줄 요약`, 50자 이내 |
| 연관 이슈 | 일반 PR은 `Refs #번호` 또는 `없음`. 릴리즈는 프로젝트의 `Closes #번호` 규칙 적용. 치환하지 않은 플레이스홀더 없음 |
| 변경 목적 | 해결하려는 문제와 이유가 구체적으로 작성됨 |
| 변경 사항 | 실제 diff와 일치하는 변경 내용. 릴리즈는 포함 PR과 릴리즈 메모 확인 |
| 검증 | 체크된 항목은 실제 결과가 있음. 미체크·미실행 항목은 사유와 남은 위험을 기록 |
| 템플릿 | develop 대상은 default, develop → main은 release |
| 시크릿 | 실제 자격증명, 비밀번호, 비밀 환경 파일이 변경에 포함되지 않음 |
| 브랜치 기반 | 대상 브랜치와 비교한 Git 근거 제시. 근거 부족은 확인 필요 |

검사 결과에는 템플릿 경로와 항목별 상태·근거를 남긴다. 제목 형식은 저장소 규칙으로 별도 확인한다. PR이 없으면 템플릿 검사는 `미확인`으로 둔다.

## 3. 코드 품질 검사

이 절차만으로 리뷰할 수 있어야 한다. 개인 환경의 보조 스킬이나 에이전트를 전제로 하지 않는다.

1. **목적과 계약 확인:** PR·이슈·요청에서 바뀌는 동작과 기대 결과를 한두 문장으로 정리한다. 요구사항이 모호하면 확인 가능한 범위와 불명확한 부분을 구분한다.
2. **테스트 먼저 읽기:** 변경된 동작의 테스트를 읽고 정상 사례, 경계 사례, 실패 사례가 무엇인지 파악한다. 테스트가 없거나 실제 동작을 검증하지 못하면 그 사실과 놓치는 동작을 기록한다. 테스트 부재만으로 심각한 결함이라고 단정하지 않는다.
3. **변경 흐름 따라가기:** 전체 diff를 확인한 뒤 변경 파일 전체와 호출부를 읽는다. 요청이 들어오는 지점부터 검증·권한 확인·상태 변경·저장·응답까지 이어지는 흐름을 추적하고, 외부 서비스나 데이터베이스를 거치면 실패했을 때의 동작도 확인한다.
4. **아래 질문으로 변경 영향 검토:** 해당 없는 항목은 억지로 문제를 만들지 말고 `해당 없음`으로 둔다.

| 관점 | 리뷰 질문 |
|---|---|
| 정확성 | 요구한 동작을 하는가? 빈 값·누락 값·경계값·잘못된 입력에서 결과가 맞는가? 실패·재시도·중복 실행 때 상태가 일관적인가? 기존 동작을 깨뜨리지 않는가? |
| 테스트 | 핵심 동작과 실패·경계 사례를 테스트가 확인하는가? 테스트가 구현 세부사항에만 결합되어 있거나 실제 회귀를 놓치지는 않는가? |
| 가독성·단순성 | 이름과 흐름만으로 의도가 전달되는가? 불필요한 중복, 복잡성, 추상화가 변경 범위에 추가되지는 않았는가? 저장소의 기존 관례를 따르는가? |
| 구조 | 책임과 모듈 경계가 자연스러운가? 의존성이 적절한 방향으로 흐르는가? 같은 문제를 해결하는 기존 코드와 충돌하거나 불필요하게 중복되지 않는가? |
| 보안·개인정보 | 외부 입력과 파일·API 데이터가 사용 전에 검증되는가? 인증뿐 아니라 해당 데이터에 대한 권한도 확인하는가? 민감정보·토큰이 응답이나 로그에 노출되지 않는가? SQL·명령·HTML 등으로 들어가는 값이 안전하게 처리되는가? |
| 성능 | 요청 수에 비례해 쿼리·네트워크 호출이 반복되지 않는가? 무제한 조회·반복이나 큰 작업이 추가되지 않았는가? UI 변경은 불필요한 렌더링이나 큰 초기 로드를 만들지 않는가? 성능 결함 주장은 측정값 또는 확인 가능한 쿼리·알고리즘 근거가 있는가? |
| 화면·접근성 (UI 변경 시) | 로딩·빈 결과·오류·성공 상태가 모두 표현되는가? 작은 화면과 키보드·스크린리더 사용에서 조작과 정보 이해가 가능한가? |
| 데이터 변경 (스키마·저장 변경 시) | 기존 데이터와 호환되는가? 제약·기본값·마이그레이션·롤백 영향이 확인되었는가? |

5. **검증 근거 확인:** 변경 유형에 맞는 테스트, 정적 검사, 빌드, 수동 확인 결과를 코드와 대조한다. 직접 실행하지 않았다면 실행하지 않은 이유와 남은 위험을 쓴다. 로그·CI 결과는 PR의 해당 커밋에서 나온 것인지 확인한다.
6. **발견 사항 검증:** 각 문제의 코드 위치와 실행 경로를 다시 따라가 발생 조건, 기대 동작, 실제 영향이 성립하는지 확인한다. 확인되지 않은 추측은 결함으로 쓰지 않고 `확인 필요` 또는 검토 한계로 분리한다.

### 검토 명령

PR 리뷰에서는 대상 base를 기준으로 커밋 diff와 파일 목록을 확인한다. 로컬 리뷰에서는 작업 트리 변경도 함께 본다.

```bash
git diff --name-only <base>...HEAD
git diff <base>...HEAD
git status --short
git diff --cached
git diff
```

미추적 파일은 diff에 자동으로 포함되지 않으므로 `git status --short`에서 확인한 뒤 내용을 직접 읽는다. PR 리뷰 결과에는 PR diff와 로컬 변경을 섞지 않는다.

이 저장소에서 관련 검증 명령을 고를 때는 변경 경로에 맞춰 실행한다.

| 변경 경로 | 검증 명령 |
|---|---|
| `frontend/` 기능·테스트 | `cd frontend && npm test` |
| `frontend/` 전체 정적 검사 | `cd frontend && npm run lint && npm run build` |
| `backend/` 기능·테스트 | `cd backend && ./gradlew test` |
| 프론트엔드·백엔드 통합 변경 | 각 영역의 관련 테스트와 정적 검사·빌드를 실행 |
| UI에서 브라우저 동작 확인이 필요한 변경 | `cd frontend && npm run test:e2e` 또는 실제 화면 수동 확인 |

변경 파일에 가까운 테스트를 우선 실행하고, 공통 모듈·인증·권한·데이터 흐름처럼 영향 범위가 넓으면 해당 영역 전체 테스트도 실행한다. 저장소 CI가 다른 명령을 쓰면 해당 workflow를 확인하고 CI 결과와 로컬 결과를 구분한다. 명령이 실패하면 원인을 조사하고, 실행할 수 없으면 미실행 사유를 기록한다.

인증·권한·결제·민감정보·외부 연동 변경은 보안 질문을 빠짐없이 확인한다. 성능 개선 PR이 아니면 프로파일링을 일률적으로 요구하지 않으며, 성능 문제를 지적할 때는 측정이나 구체적인 병목 근거를 제시한다. 보조 리뷰 도구나 별도 스킬은 팀 환경에 있을 때만 선택적으로 활용한다. 보조 도구 없이도 위 절차를 완료할 수 있어야 하며, 특정 도구가 없다는 이유로 리뷰를 중단하거나 자동 설치하지 않는다.

### 지적 심각도와 근거

| 심각도 | 기준 | 처리 |
|---|---|---|
| **Critical** | 보안 침해, 데이터 손실, 핵심 기능 중단 등 병합 시 중대한 피해가 발생할 수 있음 | 리뷰 요청 전에 수정 필요 |
| **Important** | 재현 가능한 기능 오류·회귀 또는 요구사항 누락으로 사용자가 잘못된 결과를 얻음 | 리뷰 요청 전에 수정하거나, 미해결 위험과 사유를 명시적으로 승인받음 |
| **Suggestion** | 동작 결함은 아니지만 가독성·구조·성능을 개선할 수 있음 | 선택 사항으로 제안하며 승인 차단 사유로 쓰지 않음 |

각 결함 지적에는 심각도, 파일·줄, 발생 조건 또는 재현 절차, 기대 동작과 실제 영향, 근거, 수정 방향을 포함한다. 같은 원인의 지적은 중복 나열하지 않는다. 문제를 입증하지 못한 가정은 `확인 필요`로 분리한다.

## 4. 결과 작성과 게시

다음 형태로 결과를 먼저 사용자에게 제시한다.

```text
## 셀프 리뷰 결과 (`$self-review`)

브랜치: <head> → <base> | 커밋: <개수>
검토 대상: <PR 번호·URL 또는 로컬 리뷰>
검토 시점: PR head SHA <sha 또는 해당 없음> | 로컬 HEAD SHA <sha>
미커밋 변경: <포함 여부와 파일 또는 없음>

### 템플릿
- 경로: <실제 템플릿 경로 또는 미확인>
- ✅ / ❌ / 확인 필요: <항목 — 근거>

### 코드 품질
- <심각도, 파일·줄, 재현 조건, 근거, 영향, 수정 방향>
- <발견된 문제가 없으면 그 사실과 검토 한계>

### 검증
- <실행 명령과 결과 또는 미실행 이유·남은 위험>

### 판정
<✅ 리뷰 요청 가능 / ❌ 수정 필요 / 확인 필요>
```

필수 검증이나 근거가 부족하면 `✅`로 판정하지 않는다. 게시 승인을 받은 경우 PR 번호와 저장소를 다시 확인하고 COMMENT 리뷰를 등록한다.

게시 직전에 PR의 최신 `headRefOid`를 다시 조회한다. 리뷰한 SHA와 다르면 게시하지 않고 변경된 diff를 재검토해 결과와 승인을 갱신한다. 코멘트가 남길 위험의 정확성과 적용 대상을 확인하기 위해 게시 직전 검증을 생략하지 않는다.

```bash
gh pr review <PR번호> --repo <owner/repo> --comment --body-file <리뷰본문파일>
```

본문 파일은 승인된 내용 그대로 안전한 임시 파일에 작성한다. 셸 문자열에 본문을 직접 삽입하지 않는다. 성공 여부를 확인하고, 실패하면 게시 완료라고 보고하지 않는다. PR이 없거나 게시가 승인되지 않았다면 초안만 전달한다.

## 5. 수정 승인과 반영

수정 필요 항목이 있으면 현재 상태, 제안 수정과 범위를 보여주고 명시적 승인을 받는다. 승인된 항목만 수정하고 관련 검증 및 diff 검토를 다시 수행한다.

검증을 통과하면 수정 파일만 명시적으로 stage하고 실제 변경을 설명하는 커밋을 작성한다. `git add .`는 사용하지 않는다. 승인된 push 범위와 저장소 지침을 따르고 main·develop 직접 push, force push, 브랜치 삭제는 수행하지 않는다. 검증 실패·미완료 상태를 자동 커밋·push하지 않는다.

반영 후 수정 항목, 커밋, 검증 결과, 남은 문제를 포함한 `셀프 리뷰 반영 완료` 코멘트 초안을 작성하고 게시 승인 범위에 따라 등록한다. 미해결 항목이 남으면 완료 또는 리뷰 가능으로 표시하지 않는다.

리뷰어는 develop 대상에서 상대방 팀원 1인, develop → main에서 FE·BE 담당자 모두가 필요하다. 실제 지정이나 Ready 전환을 수행하지 않았다면 완료했다고 쓰지 않는다.
