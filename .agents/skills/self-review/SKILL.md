# PR 셀프 리뷰 (Codex)

저장소 안에서 `$self-review`로 호출한다. 기존 `.claude/skills/self-review/SKILL.md`의 리뷰 흐름을 Codex용으로 적용한 스킬이다.

## 작업 원칙

- 저장소의 `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`와 변경 경로의 추가 지침을 읽는다.
- 리뷰 → 결과 게시 → 수정 승인 → 수정·검증 → 완료 게시 순서로 진행한다. 문제가 없으면 수정 단계는 생략한다.
- 리뷰 요청만으로 GitHub 게시나 코드 수정 권한을 가정하지 않는다. 게시할 내용과 대상을 먼저 제시하고 승인을 받되, 이미 명시적으로 승인된 범위는 재확인하지 않는다.
- PR 생성·리뷰어 지정·Ready 전환·병합은 별도 승인 범위에서만 수행한다. 셀프 리뷰는 팀원의 Approve를 대신하지 않는다.
- 사용자의 기존 변경을 보존하고 시크릿·개인정보를 리뷰 본문에 복사하지 않는다.

## 1. 대상과 diff 확인

저장소 루트에서 현재 상태를 확인한다.

```bash
git status --short --branch
git branch --show-current
gh repo view --json nameWithOwner
gh pr view --json number,url,title,body,baseRefName,headRefName,headRefOid,isDraft
```

사용자가 PR 번호나 URL을 지정했다면 `gh pr view`와 이후 PR 명령에 해당 대상을 명시한다. PR이 없거나 GitHub 접근이 실패하면 이유를 구분해 보고하고, 가능한 로컬 리뷰를 진행한다. PR을 임의 생성하지 않는다.

일반 리뷰의 base는 `develop`이다. PR의 실제 base가 다르면 이를 알리고 대상에 맞춰 검토한다. `develop → main`은 릴리즈 템플릿과 FE·BE 양쪽 리뷰 요건을 적용한다.

```bash
git fetch origin develop
git rev-list --count origin/develop..HEAD
git diff --stat origin/develop...HEAD
git diff origin/develop...HEAD
git log --oneline --graph origin/develop...HEAD
git merge-base origin/develop HEAD
```

릴리즈 리뷰라면 위 비교 기준을 `origin/main`으로 바꾸고 해당 ref를 fetch한다. fetch 실패 시 오래된 로컬 ref를 사용한다는 한계를 명시한다.

PR이 있으면 `gh pr diff <PR번호>`를 함께 확인한다. 로컬 HEAD와 PR의 `headRefOid`가 다르거나 미커밋 변경이 있으면 로컬 검사와 게시된 PR 검사를 구분한다. 다른 브랜치에서 실행한 테스트를 PR 검증 결과로 사용하지 않는다.

커밋이 존재한다는 사실만으로 develop에서 분기했다고 판정하지 않는다. merge-base, 커밋 그래프와 필요시 reflog를 확인하되, 생성 당시 기준 브랜치를 증명할 수 없으면 `확인 필요`로 표시한다. develop의 최신 커밋을 포함하지 않는다는 이유만으로 잘못된 분기라고 단정하지 않는다.

## 2. 템플릿 검사

실제 `.github/PULL_REQUEST_TEMPLATE/default.md` 또는 `release.md`를 읽고 PR 본문과 대조한다. HTML 안내 주석과 예시 문구를 작성된 내용으로 인정하지 않는다.

| 항목 | 기준 |
|---|---|
| PR 제목 | `타입: 한 줄 요약`, 50자 이내 |
| 연관 이슈 | 일반 PR은 `Refs #번호` 또는 `없음`. 릴리즈는 프로젝트의 `Closes #번호` 규칙 적용. 치환하지 않은 플레이스홀더 없음 |
| 변경 목적 | 해결하려는 문제와 이유가 작성됨 |
| 변경 사항 | 실제 diff와 일치하는 변경 내용. 릴리즈는 포함 PR과 릴리즈 메모 확인 |
| 검증 | 체크된 항목에 실제 결과가 있음. 미실행은 이유와 남은 위험 명시 |
| 템플릿 | develop 대상은 default, develop → main은 release |
| 시크릿 | 실제 자격증명, 비밀번호, 비밀 환경 파일이 변경에 포함되지 않음 |
| 브랜치 기반 | 대상 브랜치와 비교한 Git 근거 제시. 근거 부족은 확인 필요 |

PR이 없으면 제목·본문 검사는 미확인으로 남기고 코드 리뷰 결과만 제시한다.

## 3. 코드 품질 검사

변경 파일과 호출부, 관련 테스트를 읽고 재현 가능한 문제를 찾는다.

- 일반 코드: 정확성, 회귀, 오류 처리, 테스트 누락을 검토한다. 사용 가능한 `adversarial-reviewer` 스킬이 있으면 지침을 읽고 적용한다.
- 인증·권한·결제·외부 API: 접근 경계, 실패·재시도, 중복 처리와 민감정보 노출을 집중 검토한다. 사용 가능한 코드 리뷰 스킬을 활용한다. Claude 전용 `/code-review medium` 명령의 존재를 가정하지 않는다.
- 문서·템플릿: 논리 일관성, 모순, 가정과 실제 저장소 규칙의 일치를 검토한다. `logic-review`가 있으면 활용한다.
- 보조 스킬이 없으면 위 기준으로 직접 검토하고 그 사실을 밝힌다. 자동 설치하지 않는다.

변경에 맞는 저장소 테스트·정적 검사를 실행한다. 각 지적에 중요도, 파일·줄, 발생 조건, 영향과 수정 방향을 적는다. 추측과 확인된 결함을 구분하고, 실행하지 않은 검증을 통과로 표시하지 않는다.

수정 반영 리뷰에서는 각 지적을 수정했다는 설명만으로 해결 판정하지 않는다. 최초 실패 시나리오를 동일한 조건으로 다시 실행해 동작이 바뀌었는지 확인한다. 특히 설정 누락으로 검증 로직이 비활성화되는 경로와, 오류를 로그로 남기기만 하고 원래 실패 처리는 유지되는 경로를 확인한다. 검증에 필요한 필수 설정이 비어 있거나 테스트가 실패 경로를 실제로 밟지 않으면 해결로 표시하지 말고 `확인 필요`로 남긴다.

## 4. 결과 작성과 게시

다음 형태로 결과를 먼저 사용자에게 제시한다.

```text
## 셀프 리뷰 결과 (`$self-review`)

브랜치: <head> → <base> | 커밋: <개수>
검토 대상: <PR URL 또는 로컬 HEAD SHA>

### 템플릿
- ✅ / ❌ / 확인 필요: <항목 — 근거>

### 코드 품질
- <중요도, 파일·줄, 발생 조건, 영향, 수정 방향>
- <발견된 문제가 없으면 그 사실과 검토 한계>

### 검증
- <실행 명령과 결과 또는 미실행 이유·남은 위험>

### 판정
<✅ 리뷰 요청 가능 / ❌ 수정 필요 / 확인 필요>
```

필수 검증이나 근거가 부족하면 `✅`로 판정하지 않는다. 게시 승인을 받은 경우 PR 번호와 저장소를 다시 확인하고 COMMENT 리뷰를 등록한다.

```bash
gh pr review <PR번호> --repo <owner/repo> --comment --body-file <리뷰본문파일>
```

본문 파일은 승인된 내용 그대로 안전한 임시 파일에 작성한다. 셸 문자열에 본문을 직접 삽입하지 않는다. 성공 여부를 확인하고, 실패하면 게시 완료라고 보고하지 않는다. PR이 없거나 게시가 승인되지 않았다면 초안만 전달한다.

## 5. 수정 승인과 반영

수정 필요 항목이 있으면 현재 상태, 제안 수정과 범위를 보여주고 명시적 승인을 받는다. 승인된 항목만 수정하고 관련 검증 및 diff 검토를 다시 수행한다.

검증을 통과하면 수정 파일만 명시적으로 stage하고 실제 변경을 설명하는 커밋을 작성한다. `git add .`는 사용하지 않는다. 승인된 push 범위와 저장소 지침을 따르고 main·develop 직접 push, force push, 브랜치 삭제는 수행하지 않는다. 검증 실패·미완료 상태를 자동 커밋·push하지 않는다.

반영 후 수정 항목, 커밋, 검증 결과, 남은 문제를 포함한 `셀프 리뷰 반영 완료` 코멘트 초안을 작성하고 게시 승인 범위에 따라 등록한다. 미해결 항목이 남으면 완료 또는 리뷰 가능으로 표시하지 않는다.

리뷰어는 develop 대상에서 상대방 팀원 1인, develop → main에서 FE·BE 담당자 모두가 필요하다. 실제 지정이나 Ready 전환을 수행하지 않았다면 완료했다고 쓰지 않는다.
